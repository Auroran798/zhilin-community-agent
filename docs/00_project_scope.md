# 00 项目范围与需求冻结

## 项目背景与定位

智邻管家服务住宅小区物业场景，使用 LLM、RAG、记忆、Skills、MCP、人工审核和权限控制协助处理业务。它是可审计的业务型智能体，不是只回答问题的聊天机器人。第一版应先跑通报修工单闭环，而非同时建设复杂多智能体平台。

## 一句话介绍

居民自然语言描述诉求，系统补全信息、检索依据、在确认和授权后调用业务工具，并将高风险事项交由人工处理。

## 第一版目标

业务目标：支持四类角色；完成报修闭环；支持制度问答、模拟费用解释、公告草稿和巡检整改。技术目标：形成 Agent 状态与路由、RAG 引用、会话记忆、Skills、MCP 工具契约、权限、审计与人工审核的可实现设计。

## 第一版必须完成

- 工单创建、查询、合规状态流转、处理结果、居民评价和关闭。
- 依据文档元数据与条款引用的知识问答设计。
- 仅能保存为草稿的公告生成流程；模拟账单只读解释与核查申请；巡检转整改工单。
- 角色权限、状态机、风险边界、审计字段和可执行验收用例。

## 明确不做

真实支付、自动退款、真实门禁控制、实时摄像头分析、人脸识别、自动发布公告、A2A 多智能体协作、多小区多租户生产部署，以及自动修改账单金额或缴费状态。

## 数据使用边界

阶段 0 不创建正式数据库、不生成批量虚拟小区/住户/房屋/工单/账单/公告/巡检数据，不接触真实隐私数据。仅数据字典和验收用例可使用少量虚构示例值；阶段 1 按最终字典统一生成模拟数据。禁止长期保存身份证、银行卡完整信息、门禁密码和未经授权的家庭成员信息。

## 项目成功标准

文档中的角色、字段、状态和风险边界一致；20 条以上验收用例可判定；高风险事件均转人工；公告无人工审核不能发布；账单仅允许读取、解释和创建核查申请；进入阶段 1 的数据与接口设计可追溯。

## 术语表

| 术语 | 定义 |
|---|---|
| 居民 | 已绑定房屋、使用物业服务的用户。 |
| 工单 | 对报修或整改事项的可追踪业务记录。 |
| 人工升级 | 智能体停止自动处置，转交指定人工岗位。 |
| 公告草稿 | 未发布、必须人工审核后由人工发布的内容。 |
| RAG | 从版本化制度文档中检索证据并引用回答的机制。 |
| 幂等键 | 用于防止重复写入的唯一请求标识。 |
